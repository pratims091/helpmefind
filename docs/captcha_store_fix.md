# CAPTCHA Store Production Fix

## Problem

The CAPTCHA validation system was not working correctly in the production environment. This was due to the use of an in-memory dictionary (`captcha_store`) to store CAPTCHA challenges and their answers.

### Root Cause

The application is deployed using Gunicorn with multiple workers (3 workers as specified in `docker-entrypoint.sh`):

```bash
gunicorn --timeout 6000 --workers 3 --bind "0.0.0.0:$PORT" app:app
```

Each Gunicorn worker runs in its own separate process with its own memory space. This means that:

1. When a CAPTCHA is generated by one worker, it's stored in that worker's memory
2. If the validation request is handled by a different worker, it won't have access to the CAPTCHA data
3. This results in "Invalid or expired CAPTCHA" errors in production

## Solution

The solution was to replace the in-memory dictionary with a disk-based cache using the `diskcache` library, which was already a dependency in the project.

### Implementation Details

1. Replaced the in-memory `captcha_store` dictionary with a disk-based cache:
   ```python
   # Before
   captcha_store = {}

   # After
   captcha_cache = Cache("cache/captcha")
   ```

2. Modified the `generate_captcha()` function to use the disk cache with an expiration time:
   ```python
   # Store the challenge and answer with an ID in disk cache
   # Set expiration to 10 minutes (600 seconds)
   captcha_cache.set(
       captcha_id,
       {
           "challenge": challenge,
           "answer": answer,
           "created_at": datetime.now().isoformat(),
       },
       expire=600,
   )
   ```

3. Removed the `clean_old_captchas()` function since the disk cache handles expiration automatically

4. Updated the `require_captcha` decorator to use the disk cache:
   ```python
   # Check if the captcha_id is valid
   captcha_data = captcha_cache.get(captcha_id)
   if captcha_data is None:
       return jsonify({"message": "Invalid or expired CAPTCHA"}), 403

   # ...

   # Remove the used CAPTCHA regardless of whether answer is correct
   captcha_cache.delete(captcha_id)
   ```

## Benefits

1. **Process Independence**: All Gunicorn workers can now access the same CAPTCHA data, regardless of which worker generated it
2. **Persistence**: CAPTCHA data survives application restarts
3. **Automatic Expiration**: The disk cache handles expiration automatically, simplifying the code
4. **Scalability**: The solution will work even if more workers are added in the future

## Testing

To test this fix:

1. Run the application with multiple workers locally:
   ```bash
   gunicorn --workers 3 --bind "0.0.0.0:5000" app:app
   ```

2. Generate a CAPTCHA and verify that it can be validated correctly

3. Check that the CAPTCHA data is stored in the `cache/captcha` directory

## Future Considerations

1. **Redis Option**: For even more scalability, consider using Redis instead of disk cache if the application is deployed across multiple servers
2. **Monitoring**: Add monitoring to track CAPTCHA validation success/failure rates
3. **Rate Limiting**: Consider implementing rate limiting to further protect against abuse
